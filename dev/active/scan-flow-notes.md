# 스캔 · 발급 플로우 — 결정 기록

작성: 2026-08-19 · 브랜치 `feat/scan-flow`
> 리드가 나중에 AGENTS.md 로 합칠 초안입니다. 여기 있는 규칙은 아직 전역 규약이 아닙니다.

## 1. 화면 구성

```
/(tabs)/scan          제목 + 정사각형 카메라 하나
  └ /issue/[token]    registering → generating → ready
                                 └ error (4종 + UNKNOWN)
```

스캔 화면은 **토큰을 판정하지 않는다.** 카메라가 읽은 것을 그대로 `/issue/[token]` 으로
넘기고, 왕복과 그 실패 4갈래는 발급 화면이 전부 소유한다. 스캐너가 "잘못된 코드"를 말하려면
에러 분기 사본을 하나 더 들고 있어야 하는데, 두 벌이 되는 순간 문구가 어긋난다.

### 뷰파인더 (2026-08-19)

카카오톡 코드스캔 화면을 **레이아웃 참고용으로만** 봤다. 위에서 아래로 — 네비바, 카메라,
안내 한 줄. 그게 전부다.

- **라이트다.** 참고 화면이 어둡다고 이쪽을 어둡게 만들 이유는 없다. 앱은 라이트 전용이고
  (`grayDark` 는 import 하지 않는다), 카메라 둘레라고 예외를 두면 그게 다크모드의 시작이다.
  한 번 `solidStrong` 으로 채웠다가 되돌렸다.
- **제목은 화면 정중앙, 뒤로가기는 그 옆에 얹힌다.** 화면 헤더가 아니라 네비바다 — 제목이
  화살표가 남긴 공간의 가운데가 아니라 창의 가운데에 서야 왼쪽에 뭐가 오든 자리가 안 변한다.
  그래서 화살표는 row 로 배치하지 않고 `position: absolute` 로 얹는다.
- **카메라만 거터를 넘어간다.** 페이지에 놓인 사진이 아니라 방을 향한 창이라, 라이브 장면
  둘레의 16pt 여백은 그 장면을 사진처럼 보이게 만든다. 네비바와 안내는 거터 안에 있다.
- **무대는 카메라가 없어도 surface 로 남는다.** 프리뷰가 도착했다고 생기거나 끝내 안 온다고
  사라지면 레이아웃이 흔들린다.
- **조준 마크는 작다(56pt, 코너만).** 디코더는 프레임 전체를 읽으므로 큰 사각형은 없는 규칙을
  있는 것처럼 보이게 만들고, 사람들이 영수증을 필요 이상으로 멀리 든다. 색은 gray 1 — 아직
  아무도 보지 못한 장면 위에서 버티는 값이고, 알파 스케일이 사진 위 경계를 위해 있는 것과
  같은 이유다.
- 플래시 토글은 규약대로 **near-white 글라스**다. 아이콘은 step 12.
- 참고 화면의 **X 닫기, 앨범, 하단 3탭은 뺐다.** 하단 탭은 앱의 전역 탭바와 중복되고,
  나머지 둘은 사용자 지시(2026-08-19)다.
- 권한은 **버튼 뒤가 아니라 진입 시에 묻는다.** 스캔이라는 탭을 눌러서 온 화면에 "카메라 써도
  되나요?" 컨트롤을 또 두면 같은 질문을 두 번 하는 셈이다. `canAskAgain` 이 false 가 되면
  재요청 루프가 멈춘다. 권한이 없으면 조준 마크와 플래시도 숨는다 — 겨눌 장면이 없는데
  겨냥선을 그리지 않는다.
- `onBarcodeScanned` 는 초당 수십 번 울린다. `handled` ref 로 첫 번째만 받고, 화면에 다시
  포커스될 때 풀린다(`useFocusEffect`).

### 들어가는 길은 카메라 하나뿐이다 — 웹 포함

수동 코드 입력(2026-08-19 제거)과 앨범 업로드(같은 날 추가 후 제거) 모두 사용자 지시로
빠졌다. 남은 입력 경로는 카메라뿐이고, **플랫폼 분기는 없다.**

한동안 `Platform.OS !== 'web'` 으로 웹을 막아두고 "웹에서는 발급 불가"라고 적어뒀는데
**틀린 판단이었다.** `expo-camera` 는 `barcode-detector`(zxing-wasm 폰리필)를 의존성으로
들고 있고, 브라우저에 네이티브 `BarcodeDetector` 가 없으면 그쪽으로 폴백한다. 즉 같은
코드가 크롬에서도 QR 을 읽는다.

브라우저가 요구하는 것은 하나, **secure context** 다 (`getUserMedia`):

포트는 고정이 아니다 — `dev-up` 이 8081 부터 비어 있는 자리를 잡아 찍어 준 값을 쓴다.

| 주소 | 카메라 |
|---|---|
| `http://localhost:<포트>` (Mac 브라우저) | ✅ localhost 는 secure context |
| `exp://192.168.0.15:<포트>` (Expo Go) | ✅ 네이티브 |
| `http://192.168.0.15:<포트>` (폰 브라우저) | ❌ 평문 LAN 주소는 secure context 가 아님 |

폰 브라우저로 봐야 하면 `npx expo start --tunnel`(https) 이나 로컬 https 프록시가 필요하다.

플래시는 웹에서 `capabilities.torch` 가 있을 때만 실제로 켜진다 — 안드로이드 크롬 후면
카메라에는 있고 노트북에는 없다. 없는 기기에서는 아무 일도 안 하는데, 플래시가 없는 폰과
같은 상태라 별도 분기를 두지 않았다.

개발 중 발급 이후 화면만 확인하려면 주소로 직접 들어간다 —
`http://localhost:<포트>/issue/MCM-DEMO-2026-001`. 라우트가 토큰을 param 으로 받으므로
스캔 화면을 거치지 않아도 플로우 전체가 그대로 돈다.

## 2. 발급 화면 — 대기가 화면의 본체

`POST /cards/{id}/ai-resources` 는 202 + `PENDING` 만 주고 푸시 채널이 없다. 스피너 하나로
때우면 "기다려" 외에 아무 말도 못 한다. 실제로는 **네 가지가 따로 만들어지고 따로 끝나므로**
그 네 줄을 이름 붙여 각자 확정시킨다 — 배경 · 테두리 · 패턴 · 상품 컷. 진행은 `2/4` 로 읽힌다.

- 카드는 **등록 성공 즉시** `addCard()` 로 컬렉션에 들어간다. 고객이 기다리는 건 카드가 아니라
  카드의 옷이다.
- 리소스가 전부 실패해도 **에러 화면이 아니다.** 카드는 발급됐고 템플릿 기본 이미지를 입는다.
  "일부 디자인은 아직 생성 중입니다" 한 줄을 muted 로 붙인다.
- 실패한 줄은 색을 쓰지 않는다 — `Input` 의 규약(아이콘 + step 12 텍스트) 그대로.

### 이탈 정책 (2026-08-19 확정)

**완료까지 잡아둔다.** 발급은 제품의 감정적 핵심이고 몇 초짜리다. `registering` 과
`generating` 동안 뒤로가기 어포던스가 없고, 안드로이드 하드웨어 백과 스택 제스처도 막힌다.

**단, 잡아두는 것이 가두는 것이 되면 안 된다:**

- 생성은 서버가 한다. 화면이 사라져도 계속되고, 완료되면 카드에 반영된다.
- 그래서 **폴링 런은 화면이 아니라 모듈(`src/lib/issue-flow.ts`)이 소유한다.** 토큰별 런이
  `runs` 맵에 살고 화면은 구독만 한다. 언마운트는 구독을 끊을 뿐 작업을 죽이지 않고, 같은
  토큰으로 다시 들어오면 진행 중인 런에 그대로 붙는다.
- 20초(`PATIENCE_MS`)를 넘기면 `slow` 가 서고 **[나중에 확인하기]** 가 열린다. 90초
  (`MAX_MS`)면 폴링을 멈추고 `ready` 로 넘긴다 — 카드는 이미 있으니 실패가 아니다.
- 앱이 완전히 죽으면 맵도 사라진다. 그 경우엔 서버가 계속 만들고, 다음 진입 때 `GET` 이
  현재 상태를 읽는다.

## 3. 에러 5종 — 한 덩어리로 묶지 않는 이유

실패에서 쓸모 있는 부분은 "다음에 뭘 하느냐"뿐이고, 여기선 그게 다섯 가지 다 다르다.

| 화면이 쓰는 코드 | 1차 행동 | 2차 |
|---|---|---|
| `QR_TOKEN_INVALID` | 다시 스캔하기 | — |
| `QR_ALREADY_USED` | 컬렉션에서 보기 | 다른 영수증 스캔하기 |
| `QR_EXPIRED` | 다른 영수증 스캔하기 | — |
| `BLOCKED` | 다시 시도하기 (retry) | 컬렉션으로 가기 |
| `UNKNOWN` (네트워크·서버) | 다시 시도하기 (retry) | 컬렉션으로 가기 |

- **`BLOCKED` 은 화면의 코드이지 서버의 코드가 아니다.** 백엔드의 발급 오류는 아홉인데
  (`backend-contract.md` §2), 그중 다섯 — `CARD_TEMPLATE_NOT_FOUND` `TEMPLATE_INACTIVE`
  `TEMPLATE_CARD_TYPE_NOT_ALLOWED` `TEMPLATE_BRAND_MISMATCH` `PRODUCT_INACTIVE` — 은 고객이
  할 수 있는 일이 같다. 다섯 문장을 쓰면 다섯 다 "저희 쪽 문제입니다"의 변주가 되고,
  고객은 무엇이 다른지 알 길이 없다. `src/lib/api/registrations.ts` 의 `ISSUE_BLOCKED_CODES`.
- `BLOCKED` 와 `UNKNOWN` 만 **고객 잘못이 아님**을 문구에 명시하고 재시도를 건다. 나머지
  셋은 재시도해도 결과가 같으므로 재시도 버튼을 주지 않는다 — 특히 `QR_ALREADY_USED` 는
  다시 시도하면 또 같은 답을 준다.
- **`QR_ALREADY_USED` 에는 설명 문구가 없다.** 제목 한 줄이 이미 다 말하고, 두 개의 행동이
  아래에 서 있다. `ErrorCopy.body` 가 옵셔널인 이유가 이 한 경우다.
- 어느 코드든 **리다이렉트는 없다.** 스캔 화면은 읽은 값을 판단하지 않고 그대로
  `/issue/[token]` 으로 넘기며, 오류는 그 경로에서 제자리로 그려진다. 화면을 떠나는 것은
  고객이 버튼을 눌렀을 때뿐이다.
- 완료 화면의 `display` 는 앱 전체에서 여기 한 번만 쓴다("발급 완료").

시드(`V7`)의 `MCM-DEMO-2026-001` ~ `-011` 열한 개가 전부다. **한 번 쓰면 소멸하고**, 지금은
소진된 상태라 스캔하면 `QR_ALREADY_USED` 가 돌아온다. 되살릴 방법은 프론트에 없다 —
`POST /local/demo/reset` 은 `@Profile({"local","test"})` 라 실서버에 존재하지 않는다.
`backend-open-items.md` §6.

목 계층은 없다. `src/lib/mock/` 에 남은 것은 카드 그림과 브랜드 마크 두 파일뿐이고, 그것은
데이터가 아니라 **폴백 에셋**이다 — 서버가 주소를 주면 그쪽이 이긴다.

## 5. 아직 쓰지 않는 것 — `GET /purchase-qrs/preview`

백엔드에 **토큰을 태우지 않고 무엇이 발급될지 미리 보는** 엔드포인트가 있다:

```
GET /api/v1/purchase-qrs/preview?qrToken=…   (인증 필요)
→ { status, usable, purchaseDate, serialNumber, expiresAt, product, store }
```

지금 흐름은 스캔한 값을 그대로 `/issue/[token]` 으로 넘기고 거기서 바로 발급을 시도하므로,
**되돌릴 수 없다.** `usable` 을 먼저 물으면 쓸 수 없는 코드를 토큰을 태우지 않고 가려낼 수
있고, 발급 전에 "무엇이 발급되는지"를 보여주는 확인 단계도 가능해진다.

붙일지 말지는 결정되지 않았다. 확인 단계를 하나 더 두면 **스캔 → 카드**라는 이 화면의 요점이
흐려지고, 왕복도 하나 는다. 여기 적어두는 것은 선택지가 있다는 사실이다.
