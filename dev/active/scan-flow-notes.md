# 스캔 · 발급 플로우 — 결정 기록

## 1. 화면 구성

```
/(tabs)/scan          제목 + 정사각형 카메라 하나
  └ /issue/[token]    registering → generating → ready
                                 └ error (4종 + UNKNOWN)
```

스캔 화면은 **토큰을 판정하지 않는다.** 카메라가 읽은 것을 그대로 `/issue/[token]` 으로
넘기고, 왕복과 그 실패 4갈래는 발급 화면이 전부 소유한다. 스캐너가 "잘못된 코드"를 말하려면
에러 분기 사본을 하나 더 들고 있어야 하는데, 두 벌이 되는 순간 문구가 어긋난다.

### 카메라는 화면을 채우지 않는다 (2026-08-19 변경)

전면 뷰파인더는 스캐너 앱의 생김새다. 이 제품은 스캐너가 아니라 카드에 관한 것이고 스캔은
그 안의 한 단계이므로, **카메라는 화면의 다른 요소와 같은 크기로 페이지 안에 놓인다** —
제목과 안내가 위, 정사각형 카메라가 그 아래, 남는 공간은 비운다. 16pt 거터는 카메라를
지나쳐 끊기지 않고 이어진다.

정사각형은 **항상 정사각형이다.** 프리뷰가 도착했다고 커지거나 끝내 안 온다고 사라지면
레이아웃이 흔들린다. 카메라가 없으면 시작할 때의 surface 채움으로 그냥 남는다.

권한은 **버튼 뒤가 아니라 진입 시에 묻는다.** 스캔이라는 탭을 눌러서 온 화면이라 카메라 앞에
"써도 되나요?" 컨트롤을 한 번 더 두면 같은 질문을 두 번 하는 셈이다. `canAskAgain` 이 false
가 되면 재요청 루프가 멈춘다.

`onBarcodeScanned` 는 초당 수십 번 울린다. `handled` ref 로 첫 번째만 받고, 화면에 다시
포커스될 때 풀린다(`useFocusEffect`).

### 수동 코드 입력은 제거됨 (2026-08-19)

초기 구현에는 수동 토큰 입력 모드가 있었으나 **사용자 지시로 걷어냈다.** 화면에 남는 것은
카메라 하나뿐이다.

**대가를 알고 한 선택이다:** React Native Web 과 시뮬레이터에는 카메라가 없고
`expo-camera` 의 웹 바코드 인식은 브라우저 `BarcodeDetector` 유무에 좌우되므로,
**웹에서는 스캔 화면으로 카드를 발급할 수 없다.** 시연은 폰 기준이다.

웹에서 발급 이후 화면을 확인해야 하면 주소로 직접 들어간다 —
`http://localhost:8082/issue/MCM-DEMO-2026-001`. 라우트가 토큰을 param 으로 받으므로
스캔 화면을 거치지 않아도 플로우 전체가 그대로 돈다.

## 2. 발급 화면 — 대기가 화면의 본체

`POST /cards/{id}/ai-resources` 는 202 + `PENDING` 만 주고 푸시 채널이 없다. 스피너 하나로
때우면 "기다려" 외에 아무 말도 못 한다. 실제로는 **네 가지가 따로 만들어지고 따로 끝나므로**
그 네 줄을 이름 붙여 각자 확정시킨다 — 배경 · 테두리 · 패턴 · 상품 컷. 진행은 `2/4` 로 읽힌다.

- 카드는 **등록 성공 즉시** `addCard()` 로 컬렉션에 들어간다. 고객이 기다리는 건 카드가 아니라
  카드의 옷이다.
- 리소스가 전부 실패해도 **에러 화면이 아니다.** 카드는 발급됐고 템플릿 기본 이미지를 입는다.
  "일부 디자인은 아직 생성 중입니다" 한 줄을 muted 로 붙인다.
- 실패한 줄은 색을 쓰지 않는다 — `Input` 의 규약(아이콘 + step 12 텍스트) 그대로.

### 이탈 정책 (2026-08-19 확정)

**완료까지 잡아둔다.** 발급은 제품의 감정적 핵심이고 몇 초짜리다. `registering` 과
`generating` 동안 뒤로가기 어포던스가 없고, 안드로이드 하드웨어 백과 스택 제스처도 막힌다.

**단, 잡아두는 것이 가두는 것이 되면 안 된다:**

- 생성은 서버가 한다. 화면이 사라져도 계속되고, 완료되면 카드에 반영된다.
- 그래서 **폴링 런은 화면이 아니라 모듈(`src/lib/issue-flow.ts`)이 소유한다.** 토큰별 런이
  `runs` 맵에 살고 화면은 구독만 한다. 언마운트는 구독을 끊을 뿐 작업을 죽이지 않고, 같은
  토큰으로 다시 들어오면 진행 중인 런에 그대로 붙는다.
- 20초(`PATIENCE_MS`)를 넘기면 `slow` 가 서고 **[나중에 확인하기]** 가 열린다. 90초
  (`MAX_MS`)면 폴링을 멈추고 `ready` 로 넘긴다 — 카드는 이미 있으니 실패가 아니다.
- 앱이 완전히 죽으면 맵도 사라진다. 그 경우엔 서버가 계속 만들고, 다음 진입 때 `GET` 이
  현재 상태를 읽는다.

## 3. 에러 4종 — 한 덩어리로 묶지 않는 이유

실패에서 쓸모 있는 부분은 "다음에 뭘 하느냐"뿐이고, 여기선 그게 네 가지 다 다르다.

| 코드 | 1차 행동 | 2차 |
|---|---|---|
| `QR_TOKEN_INVALID` | 다시 스캔하기 | — |
| `QR_ALREADY_USED` | 컬렉션에서 보기 | 다른 영수증 스캔하기 |
| `QR_EXPIRED` | 다른 영수증 스캔하기 | — |
| `CARD_TEMPLATE_NOT_FOUND` | 다시 시도하기 (retry) | 컬렉션으로 가기 |
| `UNKNOWN` (네트워크·서버) | 다시 시도하기 (retry) | 컬렉션으로 가기 |

- `CARD_TEMPLATE_NOT_FOUND` 와 `UNKNOWN` 만 **고객 잘못이 아님**을 문구에 명시하고 재시도를
  건다. 나머지 셋은 재시도해도 결과가 같으므로 재시도 버튼을 주지 않는다 —
  특히 `QR_ALREADY_USED` 는 다시 시도하면 또 같은 답을 준다.
- 완료 화면의 `display` 는 앱 전체에서 여기 한 번만 쓴다("발급 완료").

## 4. 목 계층과 데모 토큰

`src/lib/mock/registrations.ts`. `mock/cards.ts` 는 이미 가진 컬렉션이고 이쪽은 영수증이
무엇으로 바뀌는지라 파일을 나눴다(`BRANDS` 만 읽어 씀).

| 토큰 | 결과 |
|---|---|
| `MCM-DEMO-2026-001` ~ `-010` | 정상 발급 (블루프린트 5종 순환, 2개 하우스·3개 매장) |
| 같은 토큰 재사용 | `QR_ALREADY_USED` — 소비 집합이 기억한다 |
| 그 외 아무 문자열 | `QR_TOKEN_INVALID` |
| `MCM-DEMO-EXPIRED-001` | `QR_EXPIRED` |
| `MCM-DEMO-NOTMPL-001` | `CARD_TEMPLATE_NOT_FOUND` |
| `MCM-DEMO-2026-010` | 정상 발급이지만 **패턴 생성만 실패** — 부분 실패 연출 확인용 |

AI 생성은 큐가 아니라 **시계**다. `POST` 는 시작 시각만 적고 매 `GET` 이 경과 시간을 읽어
그때까지 끝났을 것을 보고한다. 스케줄 1.5s / 2.8s / 4.2s / 5.6s — 넷이 동시에 뜨면 스피너로
대체 가능해지고, 이 화면이 존재하는 이유가 바로 그게 아니라는 점이다.

`USE_MOCK` 스위치는 `src/lib/issue-flow.ts` 하나뿐이다. 화면은 어느 쪽인지 모른다.

## 5. 백엔드에 확인/요청할 것

1. **`POST /cards/{id}/ai-resources` 의 요청 바디 스펙이 문서에 없다.** 프론트는
   `{ resourceTypes: ['BACKGROUND','BORDER','PATTERN','PRODUCT_ANGLE'] }` 로 가정했다.
   실서버 붙일 때 제일 먼저 깨질 자리.
2. `CardResponse.brand` (scope §5-1). 없는 동안 `toCard()` 가 시리얼 접두사(`MCM-SE-0042` → MCM)
   에서 브랜드를 유추한다. 수명 짧은 임시방편이고, 필드가 오면 세 줄이 지워질 뿐 화면은 그대로다.
   액센트는 알 수 없으므로 hex 대신 `colors.solid` 토큰을 넣는다.
3. 발급 왕복이 실제로 위 4종 코드를 그대로 주는지. 프론트는 그 문자열에 직접 분기한다.

## 7. 개발 서버 포트

이 워크트리는 **8082** 를 쓴다 (`npx expo start --port 8082`). 다른 워크트리 세션이 기본
8081 을 잡고 있어 충돌을 피하기 위함이다. 백엔드 base URL 은 기존 그대로
`EXPO_PUBLIC_API_URL ?? http://localhost:8080/api/v1`.
